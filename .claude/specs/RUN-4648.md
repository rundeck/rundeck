# SPEC: RUN-4648 - [backend] Validate step name for workflow steps

## Objective
Add backend validation so that every workflow step (created, updated, or imported via job XML/YAML) has a non-blank step name (`description` field), matching the guarantee the frontend now provides via its auto-generated default names (RUN-4929), without re-implementing or mirroring the frontend's naming algorithm itself.

## Acceptance Criteria
- [ ] A workflow step whose `description` (step name) is null, empty, or whitespace-only fails validation on job create/update -- Verification: unit test
- [ ] A workflow step with a non-blank `description` (any value, including duplicates across steps) passes validation -- Verification: unit test
- [ ] The blank-name validation is enforced on job import (XML/YAML) as part of the existing job-definition validation path (`validateJobDefinition` / `validateWorkflow` in `ScheduledExecutionService`), not just on UI save -- Verification: unit test
- [ ] A new, distinct error code/message key is added (e.g. alongside existing keys in `WorkflowStepConstants.groovy`) so blank-step-name failures are distinguishable from other workflow validation errors -- Verification: unit test
- [ ] Existing `ScheduledExecution`/workflow records already persisted with a blank step-name `description` are not retroactively broken: validation only runs against jobs going through create/update/import, not against already-stored data that isn't being re-saved -- Verification: unit test
- [ ] Duplicate step names across steps in the same workflow are NOT flagged as invalid (frontend explicitly allows duplicates by design; backend must not diverge from this) -- Verification: unit test
- [ ] No auto-generation/default-naming logic is added on the backend; blank names are rejected, never silently filled in -- Verification: unit test

## Scope
- **In scope:**
  - Backend validation (Groovy) rejecting blank/whitespace-only step names (`description` field) for workflow steps, wired into the same validation path used for job save and job import (XML/YAML).
  - A new error code/message for this specific failure.
  - Unit test coverage of the new validation logic (blank, whitespace-only, valid, and duplicate-name cases).
- **Out of scope:**
  - Any logic to auto-generate/derive a step name from plugin metadata (that is RUN-4929, frontend-only, already implemented on branch `RUN-4929-auto-logic` / PR rundeck/rundeck#10600).
  - Enforcing an exact naming pattern/convention (e.g. matching plugin title strings) — the frontend has no fixed pattern and duplicates are allowed by design, so the backend only enforces non-blank, not a specific format.
  - Retroactively validating/migrating pre-existing jobs that already have blank step names and are not being re-saved.
  - Integration/functional tests exercising the full import HTTP path (unit tests only, per engineer confirmation).
