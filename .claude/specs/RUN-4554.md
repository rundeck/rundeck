# SPEC: RUN-4554 - Deprecate API Token Acceptance via URL Query Parameter

## Objective
Deprecate the `?authtoken=` query-parameter API token auth path in `SetUserInterceptor` by adding a runtime warning and a config switch to disable it, without affecting webhook path-token auth.

## Approach
`SetUserInterceptor.groovy:62` currently reads `params.authtoken` before falling back to the `X-RunDeck-Auth-Token` header. `params.authtoken` is also populated for webhook requests, where the token is a URL *path* segment (`/api/$api_version/webhook/$authtoken`) by deliberate design (external systems like GitHub/CI POST here without custom headers) — that mechanism must be left untouched.

Chosen approach: move the existing `webhookType` detection (`controllerName == "webhook" && actionName == "post"`, currently computed at line 83) ahead of the `authtoken` extraction at line 62. For non-webhook requests only:
- If `params.authtoken` is present, read new boolean config property `security.apiTokenQueryParamAuth.enabled` via `configurationService.getBoolean("security.apiTokenQueryParamAuth.enabled", true)` (default `true`, following the existing local convention of `security.apiCookieAccess.enabled` / `security.authorization.preauthenticated.enabled` in this same file).
  - If `true` (default): behave exactly as today (extract and use the token) AND emit `log.warn(...)` noting the query-param auth path is deprecated, using `AuthenticationTokenUtils.printable(token)` to mask the token value (same masking helper already used elsewhere in this file for invalid-token logging).
  - If `false`: ignore `params.authtoken` entirely and fall back to `request.getHeader('X-RunDeck-Auth-Token')`, i.e. identical to the current "no query param sent" code path — no new error type, no request rejection.
- Webhook requests (`webhookType == true`) keep current behavior unconditionally: no warning, no config gate, `params.authtoken` (path segment) always honored.

This was chosen over gating/warning webhook requests too (would break external systems posting to webhook URLs — rejected during clarification) and over defaulting the new flag to `false` (would break existing scripts/integrations immediately on upgrade — rejected during clarification). Rejecting the request outright when disabled was also considered and rejected in favor of the simpler ignore-and-fall-back-to-header behavior, which reuses the existing "no token" code path.

Item 2 from the ticket's remediation list ("document the logging-exposure risk in the API docs") and item 3's docs implications are out of scope for this spec — no API docs directory exists in this repository (OpenAPI is generated from code annotations, no hand-written auth docs found); this was confirmed with the user and deferred.

## Acceptance Criteria

- [ ] Non-webhook API requests using `?authtoken=` still authenticate successfully when `security.apiTokenQueryParamAuth.enabled` is `true` (default), and a deprecation warning is logged with the token masked -- Verification: unit test
- [ ] Non-webhook API requests using `?authtoken=` are ignored (falling back to `X-RunDeck-Auth-Token` header, or unauthenticated if no header) when `security.apiTokenQueryParamAuth.enabled` is `false`, with no exception thrown -- Verification: unit test
- [ ] Webhook requests (`/api/$api_version/webhook/$authtoken`) continue to authenticate via the path-segment `authtoken` regardless of the new config flag's value, with no deprecation warning logged -- Verification: unit test
- [ ] Requests using the `X-RunDeck-Auth-Token` header (no query param) are unaffected by this change in all flag states -- Verification: unit test

## Scope
- **In scope:** `SetUserInterceptor.groovy` — reordering `webhookType` detection, adding the `security.apiTokenQueryParamAuth.enabled` config check, adding the deprecation `log.warn`, updating `SetUserInterceptorSpec.groovy` with new/updated test cases.
- **Out of scope:** Documenting the exposure risk in API docs (no docs location exists in this repo — deferred/separate ticket); any change to webhook path-token behavior; functional/integration-level HTTP tests (unit test coverage on the interceptor is sufficient per clarification); removing or rejecting query-param auth outright (only warn + optional disable, per ticket's remediation options 1 and 3).
